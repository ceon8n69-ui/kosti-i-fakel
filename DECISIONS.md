# DECISIONS

Решения, принятые там, где ТЗ допускает варианты. Каждое — самое простое обратимое.

## Этап 0

**D-001. Один сервис Railway на этапе 0.** API раздаёт собранную Mini App (`WEB_DIST`) и принимает вебхук бота (`/bot/webhook`). Код бота живёт в `apps/bot` как библиотека и подключается в API; для локальной разработки есть отдельный режим polling (`pnpm dev:bot`). Разделение на сервисы `api` / `bot` / `worker` — заменой команды запуска, без правок логики.

**D-002. Свой формат сессионного токена вместо JWT.** `base64url(payload).base64url(HMAC-SHA256)`, срок `SESSION_TTL_SEC` (1 час). Нет поля выбора алгоритма, одна зависимость меньше. Обновление — повторный вход по свежей `initData`, которую Telegram даёт при каждом открытии.

**D-003. Проверка `initData`.** HMAC по документации Mini Apps: в строку проверки входят все поля, кроме `hash` (поле `signature` включается). Дубли ключей отклоняются. `auth_date` старше `AUTH_MAX_AGE_SEC` (24 ч) или из будущего больше чем на 60 с — отказ. Проверка Ed25519-поля `signature` для третьих сторон не нужна: у сервера есть токен бота.

**D-004. Таблицы БД вводятся по этапам.** Этап 0 создаёт только `users` и `analytics_events`. Остальные таблицы из ТЗ 12.1 появляются в миграциях тех этапов, где начинают использоваться: так схема не застывает раньше, чем станет понятна механика.

**D-005. `telegram_id` хранится как `bigint`**, в API отдаётся строкой (идентификаторы Telegram могут выйти за 2^53).

**D-006. Событие `app_open` пишется сервером при успешном входе**, а не клиентом: его нельзя подделать и не нужен отдельный эндпоинт.

**D-007. Миграции применяются при старте API** (`RUN_MIGRATIONS=true`). Один экземпляр на этапе 0 — гонок нет. При масштабировании — отдельный шаг релиза `pnpm db:migrate`.

**D-008. Mini App без `@telegram-apps/sdk`.** Используется официальный скрипт `telegram-web-app.js` и тонкая типизированная обёртка `apps/web/src/lib/telegram.ts`: меньше бандл, меньше слоёв. Решение пересматривается, если понадобятся функции, которых нет в скрипте.

**D-009. Кнопки бота.** В личных чатах — `web_app`, если задан `PUBLIC_URL`. В группах и как запасной вариант — прямая ссылка `https://t.me/<bot>/<app>?startapp=…`; кнопки `web_app` в группах не используются (ТЗ 8.3). Параметр `startapp` фильтруется по шаблону `^(t|d|f|r)_[A-Za-z0-9_-]{1,60}$`.

**D-010. Формат граней в `balance.json`.** Грань — объект `{ t, n, taunt?, poison?, all? }`, где `t`: `M` ближний, `L` дальний, `I` магия, `B` блок (Щ), `H` лечение (С), `STAR`, `SKULL`. Буквы Щ/С заменены на B/H, чтобы ключи были латиницей. Весь стартовый баланс из ТЗ уже лежит в файле и проверяется Zod-схемой при загрузке.

**D-011. Приоритет трат Рока автоматическим мастером (стартовый):** подкрепление → +1 к атаке → перезарядка ловушки → обвал. Проверяется симулятором на этапе 2.

**D-012. Часовой пояс по умолчанию — `Europe/Kyiv`.** Telegram его не сообщает; клиент передаст настоящий на этапе 2, когда появятся тихие часы уведомлений.

**D-013. Mini App подключена как Main App бота** (режим Fullscreen). Прямые ссылки: `https://t.me/<bot>?startapp=<param>`. Если позже понадобится отдельное приложение через `/newapp`, достаточно задать `MINI_APP_SHORT_NAME`.

## Этап 1

**D-014. Вертикальный срез — сценарий `slice_cellar`** (`packages/content/scenarios/slice.json`): проход со скрытой ловушкой «Стрела» (проверки d20: заметить РАЗ, обезвредить ЛОВ), дверь, бой. На этапе 2 сценарий заменяется полноценным `DungeonDefinition`.

**D-015. Бой среза — Крысиный рой + Скелет-страж.** С тремя монстрами (добавлен лучник) одиночный Чародей в симуляции авто-ходом побеждал в 48% боёв, Знахарь — в 45%: для первого боя слишком жёстко. С двумя — 95–100% у всех классов, скелет с бронёй учит, что броня режет урон. Баланс партии и цель 2,5–3,5 раунда — задача симулятора этапа 2.

**D-016. Модель случайности.** PCG32 (XSH-RR), фиксированный поток 54, зерно — 64 бита из `crypto.randomBytes`. Значение с индексом *i* — *i*-й выход генератора; движок перематывает генератор за O(log i). Каждый бросок записывается в событие как `[индекс, граница, значение]`, поэтому после похода любой может пересчитать все броски по раскрытому зерну (`verifyJournal`). Сведение к диапазону — умножение со сдвигом (смещение ≤ n/2³², для d20 пренебрежимо). До конца похода публикуется только `sha256(seed)`.

**D-017. Состояние меняется только событиями.** `applyCommand` проверяет команду, генерирует события и применяет каждое через единственный редьюсер. Поэтому журнал — источник правды: снимок каждые 20 событий + хвост журнала дают то же состояние, что и полный пересчёт (проверяется property-тестами и интеграционным тестом с «рестартом»).

**D-018. Траектории кубиков записаны физикой заранее** (`apps/web/scripts/record-dice.mjs`, cannon-es, детерминированно): 12 бросков трёх d6 и 12 бросков d20. Сервер выбирает номер траектории тем же ГСЧ. Клиент проигрывает запись и раскладывает метки граней так, чтобы сверху оказался результат сервера. Записи принимаются, только если кубики легли ровно, далеко от бортиков и не вплотную друг к другу.

**D-019. Звёзды и черепа.** Звезда назначается вместе с индексом выбранной грани того же кубика (`star`). «Три черепа в одном броске» — только когда в этом броске участвовали все три кубика (первый бросок или переброс всех трёх).

**D-020. Броня** уменьшает каждое попадание M и L на значение брони, магия (I) и яд её игнорируют. Блок монстра (от Культиста) действует на урон героев следующего раунда и сбрасывается перед ходом врагов.

**D-021. Долг судьбы для d20** (переброс проверки за Рок) переносится на этап 2: на этапе 1 проверка разрешается сразу. Правда о мире (натуральная 20) и шрамы (натуральная 1) — механики этапа 2; на этапе 1 они дают автоматический успех/провал и эффекты на столе.

**D-022. Ход врагов.** Цели атак выбираются при показе намерений (ГСЧ), Провокация перенаправляет атаки при разрешении. Ближние атаки монстров бьют передний ряд героев, если там кто-то стоит. Урон в Тьме +1 добавляется при разрешении.

**D-023. Лимиты запросов — по пользователю**, а не по IP (игроки за одним NAT не мешают друг другу). Вход по `initData` ограничен по IP.

**D-024. Производительность одного экземпляра.** Нагрузочный тест `apps/api/scripts/load.ts`: 200 одновременных партий. При темпе живого игрока (~1 с между командами) p95 = 15 мс при цели 150 мс. Без пауз (≈400 команд/с — потолок одного процесса) p95 ≈ 510 мс: это предел пропускной способности, а не задержки. Если понадобится больше — вынос WebSocket-слоя и второй экземпляр (ТЗ 11.1).

**D-025. Клиент применяет события только для показа.** Пачка событий проигрывается анимациями, промежуточные значения считаются тем же редьюсером, а в конце пачки картинка заменяется состоянием от сервера. Решения (какие цели подсветить) принимаются по присланному состоянию.

**D-026. Сцена боя грузится лениво.** Входной чанк ~80 КБ gzip, чанк боя с Three.js и траекториями ~176 КБ. Бюджет 450 КБ в CI проверяется для первой загрузки.
